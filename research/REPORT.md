## 1. 役割分担: 何人で、どう分けると質が上がるか
**状態: 暫定まとめ（a1, a2, a4）**

**1-1. マルチエージェントの優位には条件がある**
- 並列化しやすい調査課題では、orchestrator-worker 型が単一エージェントを内部評価で +90.2% 上回った。ただしトークンは約15倍で、BrowseComp の性能分散の80%はトークン使用量だけで説明できた。[一次] https://www.anthropic.com/engineering/multi-agent-research-system
  ⚠ 例示されたのは幅優先・並列化しやすい課題で、根拠は1社の内部評価（利害関係あり）。[a4 V6]
- 思考トークン予算をそろえると、多段推論で単一エージェントがマルチエージェント構成と同等以上という報告がある。[二次] https://pith.science/paper/2604.02460 [a4 R1]
- 180構成の比較で、並列化できる課題では中央集約型が +80.8%、逐次的な推論課題では全マルチエージェント構成が 39〜70% 劣化したという報告がある。[二次] https://research.google/blog/towards-a-science-of-scaling-agent-systems-when-and-why-agent-systems-work/ [a2, a4 R2]
- → **[推測]** 「何人が良いか」は同じ予算での比較なしには答えられない。調査のように独立した部分に分けられる課題では、役割分化＋中央集約が妥当。逐次依存の強い課題では単一エージェントが妥当。

**1-2. 人数の目安**
- Anthropic: 単純な事実確認は1エージェント（3〜10ツール呼び出し）、比較は2〜4、複雑な調査は10以上。単純な問いに50体以上を起動したのが初期の失敗例。[一次] https://www.anthropic.com/engineering/multi-agent-research-system
- Claude Code agent teams: 「3〜5人から始める」「焦点の定まった3人は散漫な5人に勝ることが多い」「1人あたり5〜6タスク」。トークンと調整コストは人数に比例して増える。[一次] https://code.claude.com/docs/en/agent-teams [a5]
- ⚠ 2つとも同じ会社（Anthropic）の経験則で、独立した実証ではない。[a4]

**1-3. 同質並列と役割分化**
- 同じ役割を複製しても利得はほぼなく（<0.5%）、補完的な役割が多様性を保つ。異種モデルの混成は同質構成より最大 +47% という報告がある。[二次] https://arxiv.org/html/2606.20629 [a2]
- ペルソナ（役割名）を付与するだけでは事実問題の性能は上がらない。この論文は初版と改訂版で結論が逆転している（版確認の重要性を示す例）。[二次] https://arxiv.org/abs/2311.10054v2 [a4 R6]
- → **[推測]** 効くのは「役割名」ではなく、**担当範囲（問い・ファイル）と成果物の型の違い**。MetaGPT の SOP と構造化成果物も同じ方向。[二次] https://arxiv.org/abs/2308.00352

**1-4. 批判役・討論の効果**
- 肯定: 複数インスタンスの討論で事実性と推論が向上した（Du et al., ICML 2024）。[二次] https://proceedings.mlr.press/v235/du24e.html
- 否定: 5種の討論手法×9ベンチ×4モデルで、CoT に対して勝率20%を超えた手法はなく、トークン効率は self-consistency に劣る。モデルの異質性を入れると改善する。[二次] https://arxiv.org/abs/2502.08788 （旧題 "If Multi-Agent Debate is the Answer, What is the Question?" と同じ論文）[a4 V5]
- 外部のフィードバックがない自己修正は精度を上げず、下げることもある。→ **同じモデルの批判役は「外部のフィードバック」にならない可能性がある。**[二次] https://arxiv.org/abs/2310.01798 [a4 R4]
- 討論を重ねると同調（conformity）で全員一致の誤答に収束する、という報告が複数ある。[二次] https://arxiv.org/html/2604.02668v2 ほか。⚠ 具体的な数値（23.9%, 85.5% など）は出典の取り違えが疑われ、検証中なので結論には使わない。[a4 V3, V4]
- 「同意の強さ」の調整で、討論が最下位から最上位に変わったという報告もある。[二次] https://arxiv.org/abs/2311.17371 [a2]
- 「互いの仮説を反証させる」討論構造は、最初の説への固着（アンカリング）を防ぐと公式ドキュメントに書かれている。[一次] https://code.claude.com/docs/en/agent-teams
- → **[推測・チームの合意]** 批判役の価値は「意見」ではなく「**ツールによる外部検証**」（URL の取得、原典との照合）にある。他者の推論文ではなく、**主張と出典だけ**を受け取って独立に確かめる（CoVe の factored 方式に近い。§3）。agent4 はサイクル1からこの方針で動いている。[a2, a3, a4]

## 2. 同期・共有: 知見の共有方法と衝突・重複の防止
**状態: 暫定まとめ（a1, a2, a5）**

**2-1. 共有方式の類型**
| 方式 | 例 | 特徴 | 根拠 |
|---|---|---|---|
| 中央経由＋成果物の永続化 | Anthropic Research | 成果はファイルに保存し、リードには参照だけを返す（伝言ゲームの回避） | [一次] https://www.anthropic.com/engineering/multi-agent-research-system |
| 共有タスクリスト＋直接メッセージ | Claude Code agent teams | タスクの取得をファイルロックで排他制御し、依存関係を管理。メールボックスで直接やり取り | [一次] https://code.claude.com/docs/en/agent-teams |
| git＋ロックファイル | C コンパイラの16並列 | `current_tasks/` にファイルを置いてタスクを確保。マージ衝突はエージェントが自力で解決 | [一次] https://www.anthropic.com/engineering/building-c-compiler [a1] |
| 黒板（blackboard） | 2510.01285 | 依頼を掲示し、能力のあるエージェントが自発的に応答。13〜57% の相対改善 | [二次] https://arxiv.org/abs/2510.01285 |
| Publish-Subscribe | MetaGPT | 型付きメッセージのうち、自分に関係するものだけを購読 | [二次] https://arxiv.org/abs/2308.00352 |
- 本プロトコル（BOARD＋各自のノート）は「黒板＋ファイル所有の分割」型。ただし**ロックも依存関係も型もない**。[a2, a5]

**2-2. 重複作業**
- 委任の記述が曖昧だと重複する（例: 3体が同じ半導体不足を調べた）。対策は、目的・出力形式・ツール・**タスク境界**を明示すること。[一次] Anthropic 同上
- **本試運転で観測**: Anthropic の記事、MAST、討論の研究を 4〜5人全員が重複して調べた。調査役（agent1）と掘り下げ役の境界が定義されていなかった。[a2, a5]

**2-3. 書き込みの衝突**
- 同じファイルを2人が編集すると上書きが起きる。→ ファイルの所有を分ける。[一次] https://code.claude.com/docs/en/agent-teams
- AI エージェントの PR でマージ衝突率は約28%という二次記事がある。[二次] https://codex.danielvaughan.com/2026/07/28/agent-pr-merge-conflicts-concurrent-coding-agents-codex-cli-worktree-isolation-coordination-defence/ [a2]
- **本試運転で観測**: サイクル1で6回の push が重なったが、`pull --rebase` で全件が自動解決し、**衝突は0件**だった。BOARD は1行1エージェント＋末尾への追記で、これが効いた。[a5]

**2-4. セッション間の記憶**
- 進捗ファイルと git log を最初に読み、状態を復元する。1セッション1項目。[一次] https://anthropic.com/engineering/effective-harnesses-for-long-running-agents [a1, a5]

## 3. 品質管理: 幻覚・薄い根拠・堂々巡りの検出と抑制
**状態: 暫定まとめ（a1, a3, a4）**

**3-1. 失敗の多くは設計と検証に由来する**
- MAST: 14の失敗モードを3分類。**仕様・システム設計 44.2%／エージェント間の不整合 32.3%／タスク検証 23.5%（NeurIPS 2025 D&B 最終版）**。[二次] https://arxiv.org/abs/2503.13657 , https://proceedings.neurips.cc/paper_files/paper/2025/file/b1041e52d3be19f0a9bc491657488e4a-Paper-Datasets_and_Benchmarks_Track.pdf
  初期版では 41.8/36.9/21.3% と報告されていた。チーム内でも両方の数値が混在していた。[a4 V1]
- 個別の失敗モードでは「ステップの反復」（堂々巡り）が最も多く、15.7% という報告がある。[二次] https://arxiv.org/html/2503.13657v3 [a3]（⚠ 版は未確認）
- 検証ステップを追加すると改善するが、「コンパイルが通る」程度の表面的なチェックでは素通りする例がある。[二次] 同上 [a3]

**3-2. 検証器が決定的**
- 自律運用の鍵は質の高いテスト（C コンパイラの事例）。[一次] https://www.anthropic.com/engineering/building-c-compiler
- 研究タスクでは、LLM-as-judge（事実・引用の正確さ、網羅性、情報源の質）＋人間レビュー＋専用の CitationAgent。[一次] https://www.anthropic.com/engineering/multi-agent-research-system
- 独立検証（CoVe）: 元の草稿を**見せずに**検証の質問に答えさせると、幻覚の再生産を防げる。[二次] https://arxiv.org/abs/2309.11495 [a3]
- 品質ゲートの仕組み: agent teams では `TaskCompleted` フックで条件を満たさない完了を拒否できる。[一次] https://code.claude.com/docs/en/agent-teams
- 早すぎる完了宣言の対策: 項目ごとの合否リスト（`passes:false`）を置き、テストの削除・改変を禁止する。[一次] https://anthropic.com/engineering/effective-harnesses-for-long-running-agents

**3-3. 本試運転で実際に起きた品質問題（観測）**
1. **一次資料の遮断**: arxiv / openreview / aclanthology / HF / research.google がプロキシで 403。論文の数値は全員が検索要約経由になった。[a4]
2. **要約の誤りが全員に同時に伝播するリスク**: 全員が同じ検索要約を読むので、同じ数値が複数のノートにあっても独立の裏付けにならない。実例として、MAST の割合が版の違いで食い違い（V1）、迎合の数値で出典の取り違えが疑われた（V3, V4）。[a4]
3. **単一ソース依存**: 問い1と問い4の主要な根拠が、Anthropic の1記事に集中した。[a4 V6]
4. 自律研究エージェントでは数値の幻覚が典型的に起きる（AI Scientist の評価で7本中4本）。[二次] https://isg.beel.org/blog/2025/02/21/sakana-ai-scientist-evaluation/ [a1, a3, a4]
- LLM の引用 URL は 3〜13% が実在しないという報告がある。[二次] https://arxiv.org/html/2604.03173v1 [a4]

**3-4. 堂々巡りの検出（案）**
- 「サイクルあたりの新規出典数」を BOARD に記録し、2サイクル連続で0なら方針を変える。[推測] [a3]

## 4. コスト: トークンあたりの成果を最大化する運用
**状態: 暫定まとめ（a1, a3）**

- トークン消費はエージェントでチャットの約4倍、マルチエージェントで約15倍。価値が高く、並列化しやすい課題に限って使う。[一次] https://www.anthropic.com/engineering/multi-agent-research-system
- 実規模の例: C コンパイラは約2,000セッション／2週間、入力20億・出力1.4億トークン、約 $20,000。[一次] https://www.anthropic.com/engineering/building-c-compiler
- agent teams のトークンは人数に比例して増える。定型作業には単一セッションの方が費用対効果が高い。[一次] https://code.claude.com/docs/en/agent-teams
- 討論の早期打ち切り（合意の逐次検定）でコスト 3.7分の1、発言の選別で最大94.5%のトークン削減という報告がある。[二次] https://arxiv.org/html/2605.19193 , https://arxiv.org/abs/2502.04790 [a3]
- **プロンプトキャッシュとサイクル間隔**: キャッシュの書き込みは 5分TTL で 1.25倍、1時間TTL で 2倍、読み込みは約0.1倍。[一次] https://platform.claude.com/docs/en/build-with-claude/prompt-caching [a3]
  サイクル間隔が1時間を超えると再書き込みが発生しうるので、55分程度が安全。[推測] [a3]
- 共有ファイルは毎サイクル全文を読み直すので、ノートが肥大化すると読み込みコストが線形に増える。→ BOARD は最新状態だけにし、ノートの先頭に要約を置く。[推測] [a3]
- 未解決: 打ち切り条件の実例（AutoGen の termination 等。agent3 がサイクル2で調査予定）
