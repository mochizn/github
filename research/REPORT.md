## 結論の要約

1. **マルチエージェントの利得の大半は「トークンを並列に多く使えること」で説明できる。** 調査タスクでの +90.2%（Anthropic）も、性能分散の80%がトークン量で説明されている。予算をそろえると、単一エージェントが同等以上という報告が複数ある。したがって、無人・一晩の運用で並列化する価値は「賢くなること」ではなく、**同じ壁時計時間でより多くの調査を回せること**にある。並列化は、独立に分けられる調査に限って使う。
2. **人数は3〜5人から始める。役割は「作業の種類」ではなく「文脈（担当範囲）」で分ける。** 役割名（ペルソナ）を付けるだけでは効果がない。調査→深掘り→まとめのような作業の種類別の分割は、受け渡しで情報が落ちる。効くのは、担当範囲と成果物の型を分けることと、**書き手を1つのファイルにつき1人に限ること**。
3. **批判役は「意見を言う役」ではなく「ツールで原典を照合する検証器」にする。** 同じモデル同士の討論は同調し、予算をそろえると self-consistency に負けるという報告がある。一方、主張と出典だけを受け取って独立に確かめる検証役は安定している。本試運転でも、agent4 が出典の取り違え、版の違い、条件の脱落を計8件以上検出した。ただし、**批判役自身も誤る**（agent4 は MAST の推奨を自分で撤回した）。批判役の指摘にも同じ確度タグを付ける。
4. **品質を最も脅かしたのは幻覚ではなく「一次資料に届かないこと」と「同じ要約への全員の依存」だった。** arxiv などが遮断され、論文の数値はほぼすべて検索要約経由になった。その結果、版違い（MAST の割合が3通り）や出典の取り違え、条件の脱落が繰り返し起きた。5人が同じ数値を書いていても、独立した裏付けにはならない。
5. **PROTOCOL の改善の優先順位**（§5 で詳述）:
   - ① 初回に到達できるドメインを `ENV.md` で共有する。
   - ② 着手宣言を `claims/` のロックファイルで行い、同じ資料・同じトピックの重複を防ぐ。
   - ③ 共有の追記欄を1件1ファイルにする（BOARD の衝突は実際に3件起きた）。
   - ④ 確度タグを必須にし、まとめ役は検証済みの主張だけを結論に使う。
   - ⑤ 終了条件を「回数 OR 新しい成果ゼロ」の複合にする。
   - ⑥ 批判役とまとめ役は、他より半サイクル遅れて起動する。
   - ⑦ 手順2に git log で差分を読むことを明記し、ノートの先頭に要約を置く。

## 1. 役割分担: 何人で、どう分けると質が上がるか

### 1-1. マルチエージェントが優位になる条件
- **調査タスクでは優位だが、主因はトークン量**: orchestrator-worker 型（Opus 4 リード＋Sonnet 4 サブ）が、単一の Opus 4 を内部評価で +90.2% 上回った。トークンはチャットの約15倍で、BrowseComp の性能分散の80%はトークン使用量だけで説明できた。[一次] https://www.anthropic.com/engineering/multi-agent-research-system
  ⚠ 例示は幅優先の並列向きタスクで、根拠は1社の内部評価。[a4 V6]
- **同じ予算では単一エージェントが同等以上**: 思考トークン予算をそろえると、多段推論で単一エージェントがマルチエージェント構成と同等以上という報告がある（Tran & Kiela）。[二次] https://pith.science/paper/2604.02460
  同じ予算では CoT self-consistency が討論や Reflexion を上回り、討論は予算を増やすと逆に悪化しうるという報告もある（"Reasoning in Token Economies", EMNLP 2024）。[二次] https://aclanthology.org/2024.emnlp-main.1112/ [a4 V9]
- **課題の構造で結果が逆転する**: 180構成の比較で、並列化できる課題では中央集約型が +80.8%、逐次的な推論課題では全マルチエージェント構成が 39〜70% 劣化した。相互チェックのない独立構成はエラーを17.2倍に増やし、中央集約型では4.4倍に抑えられた（Kim et al.）。[二次・3ソースで一致] https://research.google/blog/towards-a-science-of-scaling-agent-systems-when-and-why-agent-systems-work/ [a2, a4 V7]
- **Anthropic 自身の注意**: マルチエージェントは単一エージェントの方が良い場面に使われがちで、単一エージェントのプロンプトを改善したら同等の結果が出た例がある。トークンは同等タスクで単一比3〜10倍。割に合うのは「文脈の保護・並列探索・専門化」の3場面。[一次] https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them [a1 E2, a4 V19]
- **結論 [推測]**: 一晩・無人の運用では、制約は予算より**壁時計時間とセッション数**。並列化の価値は「同じ時間で多く回せること」にある。[a2]

### 1-2. 人数
- 単純な事実確認は1エージェント（3〜10ツール呼び出し）、比較は2〜4、複雑な調査は10以上。単純な問いに50体を起動したのが初期の失敗例。[一次] https://www.anthropic.com/engineering/multi-agent-research-system
- Claude Code agent teams: 「3〜5人から始める」「焦点の定まった3人は散漫な5人に勝ることが多い」「1人あたり5〜6タスク」。トークンと調整コストは人数に比例して増える。[一次] https://code.claude.com/docs/en/agent-teams
- ⚠ どちらも同じ会社の経験則。人数について、同じ予算で比較した独立の実証は見つからなかった。[a4]

### 1-3. どう分けるか: 役割名より「文脈の境界」
- **役割名だけでは効果がない**: システムプロンプトのペルソナは事実問題の性能を改善しない。この論文は初版と改訂版で結論が逆転している。[二次] https://arxiv.org/abs/2311.10054v2 [a4 R6]
- **作業の種類別の分割は逆効果**: 計画／実装／テスト／レビューのように作業の種類で分けると、受け渡しのたびに情報が失われる。文脈の境界で分けるべき。検証サブエージェントは受け渡す文脈が最小なので安定して成功する。[一次] https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them [a1 E2, a4 V19]
- **オーケストレータなしでも回った例**: C コンパイラの16並列には、オーケストレータもロック以外の通信手段もなかった。役割は品質の観点（重複統合、性能、生成コードの効率、Rust 開発者視点の設計批評、ドキュメント）で分けていた。回った理由は「ほぼ完璧なテスト」と GCC オラクルという外部の検証器があったこと。[一次] https://www.anthropic.com/engineering/building-c-compiler [a2, a4 V12, V18]
- **書き手は1つにつき1人**: Cognition は当初「マルチエージェントを作るな」と主張したが、2026-04 に「書き込みは単一スレッドに保ち、追加のエージェントは調査・レビューを提供する」形なら機能すると立場を更新した。[二次] https://cognition.com/blog/multi-agents-working [a2, a4 V15]
- 同じ役割を複製しても利得はほぼない（<0.5%）という報告がある。[二次] https://arxiv.org/html/2606.20629 [a2]
- **本試運転への当てはめ [推測・観測]**: 本プロトコルの「調査→深掘り→批判→まとめ」は作業の種類別の分割に近い。実際に、調査役と掘り下げ役が同じ文献（Anthropic の記事、MAST、討論の研究）を4〜5人で重複して読んだ [観測]。一方、「ノートは所有者のみ」「REPORT は agent5 のみ」の単一書き手の原則は守られており、文献とも整合する。[a1, a2, a3]
- **中央集約が効く理由 [推測]**: 本質は検証点が1か所に集まることで、その役はテストが担ってもよい（C コンパイラの事例と Kim et al. を整合的に読んだ解釈）。研究タスクには自動テストがないので、出典照合役を「マージ前ゲート」として明示する必要がある。[a2]

### 1-4. 批判役・討論の効果
| 立場 | 内容 | 確度 |
|---|---|---|
| 肯定 | 複数インスタンスの討論で事実性と推論が向上（Du et al., ICML 2024）https://proceedings.mlr.press/v235/du24e.html | [二次] |
| 否定 | 5手法×9ベンチ×4モデルで、CoT に対して勝率20%を超えた討論手法はない。トークン効率は self-consistency に劣る。異質なモデルを混ぜると改善（"Stop Overvaluing Multi-Agent Debate"、旧題 "If Multi-Agent Debate is the Answer, What is the Question?"）https://arxiv.org/abs/2502.08788 | [二次] |
| 否定 | 外部フィードバックのない自己修正は精度を上げず、下げることもある https://arxiv.org/abs/2310.01798 | [二次] |
| 否定 | 討論で正→誤の変化が起き、長いほど劣化する。**弱いモデルを混ぜると強いモデルも劣化し、多様性では失敗が解消しない**（"Talk Isn't Always Cheap"）https://arxiv.org/abs/2509.05396 | [二次] |
| 否定 | 多数派への同調（多数派回答の採用が最大85.5%）https://arxiv.org/pdf/2605.00914 ／ 3ラウンドで意見の割れた問題の23.9%が全員一致の誤答に収束 https://arxiv.org/pdf/2604.07667 | [二次]（出典はサイクル2で訂正済み [a2, a4 V3/V4]） |
| 条件付き肯定 | 「同意の強さ」を調整すると、討論が最下位から最上位に変わる https://arxiv.org/abs/2311.17371 | [二次] |
| 条件付き肯定 | 互いの仮説を反証させる構造は、最初の説への固着（アンカリング）を防ぐ https://code.claude.com/docs/en/agent-teams | [一次] |

- **「異質なモデルを混ぜれば効く」は未確立**: 2502.08788 と 2509.05396 は衝突している。入れるなら「能力が同等以上の別モデル」か「別の情報源」に限る、という条件付きでしか言えない。[a4 V10]
- **結論**: 批判役の価値は意見ではなく**ツールによる外部検証**にある。他者の推論文ではなく、主張と出典の組だけを受け取り、自分で原典を開いて照合する（CoVe の factored 方式に相当。§3）。本試運転の agent4 はこの方針で、V1〜V20 の照合を行い、出典の取り違え（V3/V4）、版の混同（V8a）、分母の取り違え（V14）、まとめ役の誤認（V16）を検出した。[観測]

## 2. 同期・共有: 知見の共有方法と衝突・重複の防止

### 2-1. 共有方式の類型
| 方式 | 例 | 長所 | 短所 | 根拠 |
|---|---|---|---|---|
| 成果物の永続化＋参照の受け渡し | Anthropic Research | 伝言ゲームとトークン浪費を避けられる | 中央に集約の負荷が集まる | [一次] https://www.anthropic.com/engineering/multi-agent-research-system |
| 共有タスクリスト＋メールボックス | Claude Code agent teams | タスク取得をファイルロックで排他制御し、依存関係を自動で解決 | 状態更新の遅れ、リードの早すぎる終了 | [一次] https://code.claude.com/docs/en/agent-teams |
| git＋ロックファイル | C コンパイラの16並列 | `current_tasks/` を push し、競合したら負けた側が別タスクを選ぶ | マージ衝突は頻繁（エージェントが自力で解決） | [一次] https://www.anthropic.com/engineering/building-c-compiler |
| 黒板（blackboard） | Salemi et al. | 能力に応じて自発的に引き受ける。13〜57% の相対改善 | — | [二次] https://arxiv.org/abs/2510.01285 |
| Publish-Subscribe | MetaGPT | 型付きメッセージのうち、関係するものだけを購読 | — | [二次] https://arxiv.org/abs/2308.00352 |
| 構造化ノート | context engineering | 文脈の外に記録し、後で読み戻す | 読み戻すコストが増える | [一次] https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents |

- 本プロトコルは「所有権付きのノート（私的）＋BOARD（共有）」の hybrid 型。ただし**ロック・依存関係・メッセージの型がない**。黒板型とは、自発的に引き受けるのではなく役割が固定されている点で異なる。[a2, a4 V11]
- 掲示板・共有ファイル・直接メッセージを同じ条件で比較した実証研究は見つからなかった。[a2]

### 2-2. 重複作業 [観測が中心]
- 文献: 委任の記述が曖昧だと重複する（3体が同じ半導体不足を調査した）。目的・出力形式・ツール・タスク境界を明示する。[一次] Anthropic 同上
- 本試運転で観測された重複:
  - (a) arxiv の遮断の発見と迂回を5人全員が別々に試した（agent4 は約10ドメインを試行）。
  - (b) Anthropic の記事と MAST を4〜5人が独立に取得して要約した。
  - (c) MAST の割合の照合を、サイクルをまたいで3人が繰り返した。[a2, a3, a4]
  → 初回の環境情報の共有と、**資料単位の着手宣言**があれば避けられた。

### 2-3. 書き込みの衝突 [観測]
- 文献: 同じファイルを2人が編集すると上書きが起きる。ファイルの所有を分ける。[一次] https://code.claude.com/docs/en/agent-teams
- **本試運転で BOARD.md の衝突が3件起きた**（agent3 が1件、agent4 が2件）。いずれも「誰でも追記可」の論点リスト・疑義欄の末尾への追記が原因で、自動で解決できず手動で解決した。agent4 は一度、rebase の途中で push に失敗している。表の自分の行の更新だけなら衝突しなかった。[a3, a4 V16]
- **まとめ役の誤認**: agent5 はサイクル2で「衝突0件」と書いたが、自分の push だけを見た誤りだった。集約役は自分の視点に偏るので、運用の事実も各エージェントの自己申告で集めるべき。[観測]
- 参考: AI エージェントの未マージ PR 10.7万件の模擬マージで27.67%が衝突したという報告がある。ただし上流の進行との衝突で、本件の同時追記とは状況が異なる。[二次] https://github.com/unlv-evol/AgenticFlict [a4 V14]

### 2-4. セッション間の引き継ぎ
- 進捗ファイル（claude-progress.txt）と git log を最初に読み、機能リストで次の項目を決め、既存の動作を確認してから新規作業に入る。1セッション1項目。[一次] https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents
  ⚠ この記事は**逐次の単一エージェント構成**（プロンプトだけを変えた同じハーネス）なので、根拠になるのは「セッション間の引き継ぎ」まで。並列同期の根拠にはならない。[a4 V13]
- 本プロトコルの手順2（全部を読む）には「前回からの差分」を得る手段がない。→ `git log <前回の自分のコミット>..HEAD --stat` で差分を読む。[推測] [a2]

### 2-5. 依頼の往復遅延 [観測]
- サイクル1で書いた依頼はサイクル2で処理され、REPORT への反映はサイクル3になった。3サイクルの試運転では、依頼→検証→修正が**1往復しかできない**。agent4 のサイクル1は、他者のノートが空の状態で始まった。[a2, a4]

## 3. 品質管理: 幻覚・薄い根拠・堂々巡りの検出と抑制

### 3-1. 失敗の分類（MAST）
- 14の失敗モードを3分類（仕様・システム設計／エージェント間の不整合／タスク検証）。失敗の主因はモデルの能力より設計と協調にある。[一次: FM 定義] https://raw.githubusercontent.com/multi-agent-systems-failure-taxonomy/MAST/main/taxonomy_definitions_examples/definitions.txt
- **3分類の割合は版によって異なる**ので、1つの数値は使わない。
  - 41.8/36.9/21.3%（初期版とされる）[二次]
  - 44.2/32.3/23.5%（NeurIPS 2025 版とされる）[二次]
  - 37.17/31.41/31.41%（公式リポジトリの図 taxonomy_v11）[一次] https://raw.githubusercontent.com/multi-agent-systems-failure-taxonomy/MAST/main/assets/taxonomy_v11_cropped-1.png
  - **全版で安定して言えるのは「仕様・設計が最大」だけ**。検証と協調の順位は版によって入れ替わる。[a1 E1, a4 V17]
- 本テーマに関係する失敗モード（名称は公式定義）: FM-1.3 Step Repetition（堂々巡り）、FM-1.5 Unaware of Termination Conditions、FM-3.1 Premature Termination、FM-3.2 Weak Verification、FM-3.3 No or Incorrect Verification。[一次] [a3]
- 検証ステップを追加すると成功率が上がる（ChatDev で +15.6%）。ただし「コンパイルが通る」程度の表面的な検証では素通りする。[二次] https://arxiv.org/html/2503.13657 [a3, a4 V8b]

### 3-2. 検証器の設計
- **外部の検証器が決定的**: 自律運用の成功例（C コンパイラ、長時間ハーネス）は、どちらも自動テストという強い検証器を持っていた。研究タスクにはそれがないので、成功例をそのまま当てはめてはいけない。[一次] [a4 V12, V13]
- **研究タスクの代替**:
  - LLM-as-judge（事実・引用の正確さ、網羅性、情報源の質）＋人間レビュー＋専用の CitationAgent。[一次] https://www.anthropic.com/engineering/multi-agent-research-system
  - 引用 URL に到達できるか、引用文と一致するかのチェック。[推測]
- **独立検証（CoVe）**: 元の草稿を見せずに検証の質問に答えさせると、幻覚の再生産を防げる。FActScore は factored 版で 55.9→63.7、factor+revise 版で 71.4。ただし factored 版は1回答あたりの事実数が 16.6→11.7 に減る（**正確さと網羅性のトレードオフ**）。[二次] https://arxiv.org/abs/2309.11495 [a3, a4 V8a]
  → 批判役が主張を削るほど「見かけの正確さ」は上がるが、網羅性は落ちる。[推測]
- **同じモデルの評価者は甘くなる**: LLM の評価者は自分の生成文を好む傾向がある。[二次] https://arxiv.org/abs/2410.21819 [a3]
  → 「読んで良し悪しを判断する」より「主張を抜き出して出典を開き直す」方がよい。
- **品質ゲート**: agent teams の `TaskCompleted` フックで、条件を満たさない完了を拒否できる。[一次] https://code.claude.com/docs/en/agent-teams
  長時間ハーネスでは、テストの削除・改変を禁止し、`passes:false` の項目リストを置く。[一次] https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents

### 3-3. 堂々巡りの検出
- **実装例 HolmesGPT**: 直近8ターンで、同一ツール呼び出しの反復、A/B の交互反復、エラーの反復、言い換えただけの同じ主張（類似度0.8以上）、退化した応答を検出する（閾値3回）。まず警告し、2回無視したらツールを取り上げて結論を強制する。[一次] https://github.com/HolmesGPT/holmesgpt/pull/2433 [a3]
- CAMEL のロールプレイの失敗: 役割の入れ替わり、オウム返し、「やります」とだけ言う空返事、終わらないループ。[二次] https://arxiv.org/abs/2303.17760 [a1 E6]
- 自己修正では直らない（§1-4）ので、**本人の判断ではなく機械的なカウンタで止める**。[推測] [a3]
- **本試運転での堂々巡りの実例** [観測]: 一次資料が取れない MAST の割合の照合を、サイクルをまたいで複数人が繰り返した。→ 「同じ要確認の項目が2サイクル続いたら『⚠未確認』で確定して打ち切る」ルールで止められた。[a3]

### 3-4. 本試運転で実際に起きた誤りの型 [観測]
| 型 | 実例 | 検出者 |

## 4. コスト: トークンあたりの成果を最大化する運用

### 4-1. 相場
- トークン消費: エージェントでチャットの約4倍、マルチエージェントで約15倍。同等タスクの単一エージェント比では3〜10倍。[一次] https://www.anthropic.com/engineering/multi-agent-research-system , https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them
- 実規模の例: C コンパイラは約2,000セッション／2週間、入力20億・出力1.4億トークン、約 $20,000。[一次] https://www.anthropic.com/engineering/building-c-compiler
- agent teams のトークンは人数に比例して増える。定型作業には単一セッションの方が費用対効果が高い。[一次] https://code.claude.com/docs/en/agent-teams

### 4-2. 打ち切り条件
- AutoGen は終了条件を部品化している（MaxMessage, TokenUsage, Timeout, TextMention, External など）。OR と AND で合成でき、チームには終了条件が必須。[一次: ソース] https://raw.githubusercontent.com/microsoft/autogen/main/python/packages/autogen-agentchat/src/autogen_agentchat/conditions/__init__.py [a1 E5, a3]
- 討論の早期打ち切り（合意の逐次検定）でコスト 3.7分の1、発言の選別で最大94.5%のトークン削減という報告がある。[二次] https://arxiv.org/html/2605.19193 , https://arxiv.org/abs/2502.04790 [a3]
- 本プロトコルの終了条件は「3サイクル」という回数制限だけ。成果が出ないときの停止や、トークンの上限がない。[a1, a3]

### 4-3. サイクル間隔とキャッシュ
- プロンプトキャッシュの書き込みは 5分TTL で 1.25倍、1時間TTL で 2倍、読み込みは約0.1倍。[一次] https://platform.claude.com/docs/en/build-with-claude/prompt-caching
- 本試運転の間隔は実測で約57分で、1時間TTL の内側に収まった。[観測] [a3]
- トリガーが遅れて60分を超えると、会話全体の再書き込みが起きうる。→ 間隔は 50〜55分が安全。[推測]
- 間隔を短くすると依頼への応答も早くなる（§2-5）。コストとのトレードオフ。[推測] [a2]

### 4-4. 読み込みコスト
- サイクル2の開始時点で、共有ファイルは約350行あった。全員が毎サイクル全部を読むので、読み込み量は「人数×総行数」で、サイクルごとに増える。[観測] [a3]
- 対策:
  - ノートの先頭に「最新サイクルの要点（5行）」を置く。
  - 差分は git log で読む（§2-4）。
  - 同じ資料は1人だけが読み、他の人は要約を参照する（§2-2）。[推測]

## 5. 結論: 本 PROTOCOL.md の改善提案

採用の基準は「本試運転で観測された問題があること」と「外部に根拠があること」。優先度は、観測された実害の大きさで付けた。

| 優先 | 提案 | 解決する観測問題 | 根拠 |
|---|---|---|---|
| ★1 | **`ENV.md` を初回に作る**: 最初に起動したエージェントが主要ドメインへの到達性を確認して記録する（取得可: anthropic.com, claude.com, raw.githubusercontent.com ／ 不可: arxiv, openreview, aclanthology, HF ほか）。迂回経路も追記する | 遮断の発見と迂回を5人が重複した。二次要約への依存 | [観測] a2, a4／MAST（検証失敗） |
| ★2 | **確度タグを必須にする**（[一次]/[二次]/[推測]）。[二次] には参照した要約の URL も書く。まとめ役は「[一次] または批判役が ✔ を付けた [二次]」だけを結論に使い、その他は ⚠ を付けて併記する。**批判役の指摘も同じタグで扱う** | 版違い・出典の取り違えが結論に入りかけた。批判役自身も誤った | [観測] V1, V3, V4, V8a, V17／CoVe [二次] |
| ★3 | **`claims/<agent>-<topic>.md` のロックファイル**: トピックや資料（主要文献）単位で、着手時に作って push する。既にあれば別のものを選び、完了時に要約へのリンクを残す | 同じ文献を4〜5人で重複して読んだ | [観測]／C コンパイラ事例、agent teams のファイルロック [一次] |
| ★4 | **共有の追記欄を1件1ファイルにする**: 論点・疑義・依頼を `board/<type>/<agent>-<n>.md` に分ける。BOARD.md の表は「自分の行だけ」の更新に限定する | BOARD の衝突が3件（手動解決、push 失敗1回） | [観測] V16, a3／agent teams「ファイルの所有を分ける」[一次] |
| ★5 | **役割を「文脈単位」に寄せる**: 問いごとに「調査＋深掘り＋自己検証」を1人が受け持つ（例: 4人×各問い）。批判役は「主張と出典の組だけを受け取って照合する」専任の検証役として残し、**マージ前ゲート**（✔ を付けるまで REPORT に入れない）と明記する。書き手は1ファイル1人を維持する | 調査役と掘り下げ役の境界があいまいで重複した。作業の種類別の分割による情報の欠落 | [観測]／claude.com「文脈境界で分けよ」[一次]、Cognition single writer [二次] |
| ★6 | **終了条件を複合にする**: 「Nサイクル OR 2サイクル連続で新規出典0かつ新規主張0 OR 依頼が無い」で DONE。BOARD の各行に「新規出典数」の欄を設ける。同じ要確認の項目が2サイクル続いたら「⚠未確認」で確定し、打ち切る | MAST の割合の照合の繰り返し（堂々巡り） | [観測]／AutoGen 終了条件 [一次]、HolmesGPT [一次] |
| ★7 | **起動をずらす**: 調査役と掘り下げ役は T=0、批判役とまとめ役は T+30分。または初回の役割を「批判役＝検証基準の作成、まとめ役＝骨組み作成」と明記する | 批判役とまとめ役の初回が空のノートから始まった | [観測] a2, a4, a5 |
| ★8 | **差分を読むことを手順2に明記する**: `git log <前回の自分のコミット>..HEAD --stat`。ノートの先頭に「最新の要点5行」を置き、他人はまずそこだけを読む | 読み込みコストが人数×総行数で増える | [観測] a3／[推測] |
| ★9 | **サイクル数と間隔**: 依頼の往復が最低2回できるよう、4〜5サイクル以上にする。間隔は 50〜55分。依頼が無いサイクルは読むだけで短く終える | 3サイクルでは依頼→検証→修正が1往復しかできなかった | [観測] a2／prompt caching [一次] |
| ★10 | **決定事項ログ**: 用語の訳語、採用した数値の版、確度タグの定義など、チームの暗黙の決定を `DECISIONS.md` に1行ずつ書く | 確度タグの表記が人によって違った（[原文確認]/[一次]/[要約経由]/[二次]） | [観測]／Cognition「暗黙の決定の衝突」[二次] |

### PROTOCOL v2 の差分（案）
```
## 場所（追加）
- ENV.md          初回に作成。到達できるドメインと迂回経路（誰でも追記可、1行1ドメイン）
- DECISIONS.md    チームの決定事項（用語・採用した版・タグ定義）
- claims/         着手ロック。<agent>-<topic>.md を着手時に push、完了時に要約へのリンクを書いて close
- board/{issues,requests,doubts}/<agent>-<n>.md   共有の追記はすべて1件1ファイル

## 1サイクルの手順（変更点）
2. git log <前回の自分のコミット>..HEAD --stat で差分を確認し、変わったノートの「最新要点」だけを読む
3. 着手前に claims/ を確認し、自分の claim を push してから作業する
4. 主張には確度タグ [一次]/[二次]/[推測] を必須とし、[二次] には参照した要約の URL も書く
5. BOARD の自分の行に「新規出典数/新規主張数」を記入する

## 終了条件（変更）
- 最大 N=5 サイクル、または 2サイクル連続で新規出典0かつ新規主張0、または 自分宛ての依頼が0で役割の作業が完了 → STATUS: DONE

## 役割（変更）
- 批判役はマージ前ゲート: ✔ の付いていない [二次] の主張は、REPORT では ⚠ 付きでしか使えない
- 起動時刻: 批判役とまとめ役は他より30分遅らせる
```

### 本試運転についての総括 [推測を含む]
- うまくいったこと:
  - ファイル所有の分割（自分のノートと REPORT の単一書き手）で、成果物どうしの衝突は起きなかった。
  - 批判役がツールによる照合に徹し、少なくとも8件の誤りを結論に入る前に止めた。
  - 確度タグが自然発生的に導入された。
- うまくいかなかったこと:
  - 一次資料の遮断による二次情報への依存。
  - 同じ文献の重複読み。
  - 共有追記欄の衝突。
  - 依頼の往復が1回しかできなかったこと。
  - まとめ役が自分の視点だけで運用の事実を判断したこと。
- **最も効果が大きいと見込む改善は ★1〜★3**（環境の共有、確度タグとゲート、資料単位の claim）。いずれも実装コストが低く、今回の実害に直接対応する。
