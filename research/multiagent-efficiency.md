# 複数エージェント運用を「同じ成果をより少ないトークンで」やる方法

作成: 2026-10-10 リーダーセッション。材料は (1) 今回の織り込み分析（5人×7ラウンド）の実測トークン、(2) Anthropic の公式資料（出典は末尾）。[実測]＝セッションの usage から計算、[公式]＝公式資料に書いてあること、[推測]＝見積もり。

---

## 1. 結論（先に3行）

1. **今回のお金の8割は「考えた量」ではなく「読み直した量」に消えた**。出力（実際の作業）は全体の13%。残りは、50万トークン近くまで膨らんだ各エージェントの会話を毎ターン読み直す分（35%）と、休止後に作り直す分（47%）[実測]
2. いちばん効くのは **「長生きする5セッション＋リーダーが10分おきに起こす」方式をやめ、ラウンドごとに短い新しい文脈で動かす**こと。状態は会話ではなくファイルに置く。最終ラウンドは作業量の割に約 $26 かかったが、うち $17 は文脈の作り直しで、出力は $0.8 だった [実測]
3. 仕組みとしては Claude Code の **dynamic workflow（ultracode）** が今回の用途にほぼそのまま合う。計画と途中結果をスクリプトが持ち、エージェントは毎回まっさらな文脈で走り、段階ごとにモデルを変えられ、並列の兄弟でキャッシュを共有できる [公式]

---

## 2. 今回どこにトークンが消えたか [実測]

織り込み分析チーム（子5人）の最終 usage（合計 $117.9、Opus 5.5 の単価で按分）:

| 種類 | トークン | 金額の目安 | 割合 | 中身 |
|---|---|---|---|---|
| キャッシュ読み | 2億450万 | 約 $41 | 35% | 毎ツールコールのたびに、膨らんだ会話（最後は 43〜55万トークン）を読み直す |
| キャッシュ書き | 751万 | 約 $55 | 47% | 会話の伸びの分＋**1時間以上休んだ後の再開で会話全体を書き直す分** |
| 出力 | 74万 | 約 $15 | 13% | 実際に書いた分析・コード・コミット |
| 入力（非キャッシュ） | 169万 | 約 $7 | 6% | |

さらに **リーダー（このセッション）が別に約 $43**（3プロジェクト分、文脈 38万トークン）。巡回のたびに大きな文脈を起こして「まだ作業中か」を確認していた。

**最終ラウンド（訂正だけ）の内訳**: キャッシュ書き 236万トークン（約 $17）＋読み 3,170万（約 $6）＋出力 3.9万（約 $0.8）。5人が3日休んでいたので、作業を始める前に各自の 45万トークンの会話を作り直した。**作業そのものの30倍を準備に払った**。

公式資料の傾向とも一致する: 「マルチエージェントはチャットの約15倍のトークンを使う」「長いセッションは毎回会話全体を送るので、1行の質問でも会話全体分を消費する」「キャッシュの寿命（サブスクは1時間）を過ぎた最初のメッセージは全文を再処理する」[公式]

## 3. 改善策（効く順）

### ① 文脈を短く保つ ― 状態は会話ではなくファイルに（効果: 大）
- **ラウンドごとに新しいセッション（または /clear）で始める**。各エージェントは「BRIEF＋自分の担当ファイル＋1ページの引き継ぎメモ」だけ読んで始める。今回のように同じセッションへ send_message し続けると、7ラウンド分の会話を毎回背負う
- 見積もり: 1ラウンドの文脈を 50万→5〜8万トークンにすると、読み・書きの単価が約1/7。今回の $118 は **$30〜50 程度**になった可能性 [推測]
- 引き継ぎメモは「決まったこと・未解決・次にやること」だけ（2千トークン以内）。他人のカードは全文でなく要約ファイルを読む（今回は5人がそれぞれ全員のカードを毎ラウンド読み直していた）

### ② 「LLM が LLM を見張る」をやめ、スクリプトに順番を持たせる（効果: 大）
- 今回: リーダーが10分おきに起き、38万トークンの文脈で状態を確認 → 子に指示 → また寝る。確認のたびに大きな文脈を読む
- **dynamic workflow**: Claude が JavaScript のスクリプトを書き、ランタイムが `agent()`／`parallel()`／`pipeline()` で子を動かす。途中結果はスクリプトの変数に残り、親の文脈には最終結果だけが入る。待つのは LLM ではなくランタイムなので、見張りのトークンがゼロ [公式]
- 付いてくる利点 [公式]:
  - 同じモデル・同じ設定で並列に起動したエージェントは、**最初の1体のキャッシュを他が読む**（最大5秒ずらして起動して共有）
  - 段階ごとにモデルを指定できる（集める段は軽いモデル、まとめる段は Opus）
  - 中断しても同じセッションなら完了済みの結果を再利用して再開できる。利用上限に当たると、条件付きでリセットを待って自動で続く
  - 出力を JSON スキーマで縛れる（受け渡しが短く正確になる）
  - 規模の目安（`workflowSizeGuideline`: small＝5体未満〜large＝50体未満）と、25体超または 150万トークン超で警告
- 使い方: プロンプトに `ultracode` と書く、または「ワークフローで」と頼む。調査なら組み込みの `/deep-research` がそのまま近い（多角的に検索 → 照合 → 主張ごとに投票 → 出典つきレポート）

### ③ 段階ごとにモデルと effort を分ける（効果: 中〜大）
- 価格（100万トークンあたり、入力/出力）: Opus 5.5 $4/$20、Sonnet 5.5 $2/$10、Haiku 5.5 $0.10/$0.50 [公式]
- **データ集め（株価の取得、開示の抜き出し、表の整形）は Haiku 5.5／Sonnet 5.5、判断と統合だけ Opus**。Anthropic の研究システムも「Opus のリーダー＋Sonnet の子」で単体の Opus より 90% 良かった [公式]
- 注意: Sonnet 5.5 のキャッシュ読みは Opus 5.5 と同じ $0.20。文脈が長いままモデルだけ下げても読み直し分はあまり減らない → ①が先
- effort: 調査・知識作業は effort の差で精度がほとんど変わらず、low で費用が1/3〜1/2 減った例がある。子は low〜medium、統合だけ medium〜high が目安 [公式]

### ④ 決まった計算・取得はコードで（効果: 中）
- 今回も株価取得・逆算はスクリプト化して効いた。さらに「開示文書を取ってきて数字を抜く」もスクリプトでやり、LLM には抜いた数字だけ渡す。長いページを丸ごと文脈に入れない
- Claude Code なら hook で出力を絞る（例: テスト結果は失敗行だけ返す）、skill で前提知識を渡して探索を省く [公式]

### ⑤ 人数とラウンドを課題に合わせる（効果: 中）
- 公式の目安: 単純な事実確認は1体・ツール3〜10回、比較は2〜4体・各10〜15回、複雑な調査は10体超 [公式]
- マルチエージェントが得なのは「並列にできる」「1つの文脈に入りきらない」作業。共有文脈が多い・依存が強い作業は単体の方が安い [公式]
- 今回の8銘柄は「銘柄ごとに独立に集めて分析」までは並列向き、「銘柄間の整合・統合」は1体向き。ラウンドを7回回すより、**集める（並列）→ 分析（並列）→ 反証（並列）→ 統合（1体）** の4段で足りた可能性 [推測]

### ⑥ 検証は「全部読み直す」でなく「主張ごとに当てる」（効果: 小〜中）
- 今回の相互チェックは、他人のカードを丸ごと読んだ。代わりに「重要な主張 20個」を抜き出し、主張ごとに短い検証エージェントを当てて投票する（`/deep-research` の方式）。読む量が主張の数に比例するだけで済む

### ⑦ キャッシュの扱い（効果: 小〜中、①②を採れば自然に解決）
- 同じセッションを1時間以上止めてから再開すると、全文を作り直す。止めるなら「次は新しい文脈で始める」前提にする
- 巡回が必要なら、大きなリーダーを起こすのではなく、**毎回まっさらな小さいセッションを起こす**トリガー（create_new_session_on_fire）で、状態はファイルから読む

## 4. 次回の設計案（同じ「光関連株の織り込み分析」をやるなら）

1つのクラウドセッションで、ワークフロー1本:

| 段 | 何を | 体数 | モデル・effort | 受け渡し |
|---|---|---|---|---|
| 0 計画 | 論点と出力スキーマを決める | 1（自分） | Opus medium | BRIEF.md |
| 1 収集 | 銘柄ごとに株価・開示・アナリストを集め、数字だけ JSON に | 8 | Sonnet 5.5 or Haiku 5.5、low | data/<銘柄>.json |
| 2 分析 | 銘柄ごとに「織り込み」の逆算と候補を書く（自分の銘柄のデータだけ読む） | 8 | Opus 5.5 medium | stocks/<銘柄>.md |
| 3 業界 | 共通前提（capex・供給能力・CPO）を1本 | 1 | Opus medium | sector.md |
| 4 反証 | 重要な主張 20〜30個を1個ずつ検証、3体で投票 | 60〜90（短命） | Sonnet 5.5 low | claims.json |
| 5 統合 | 要約と表、銘柄間の矛盾 | 1 | Opus high | REPORT.md |

- 文脈はどのエージェントも短命で 5〜10万トークン以内。見張り役なし
- 見積もり: 今回（子 $118＋リーダーの相当分）の **1/3〜1/2 程度** [推測]。精度は、反証を主張ごとの投票にする分むしろ上がる見込み
- 先に小さく試す: 2銘柄だけで回して、`/workflows` の画面でエージェントごとのトークンを見てから全体を回す [公式の推奨]

## 5. やらなくていいこと
- **context editing（古いツール結果の削除）は節約手段ではない**。削るたびにキャッシュを作り直すので、測ったら削減より費用増の方が大きかった例がある [公式]
- **agent teams**（常駐する仲間のセッション）は、標準セッションの約7倍のトークン。長く走らせる仲間は少人数・短時間に [公式]
- モデルを会話の途中で切り替える（キャッシュがモデルごとなので作り直しになる）。切り替えるなら段の境目で [公式]

## 6. 限界
- 金額は Opus 5.5 の API 単価で按分した目安。サブスクの「5時間枠・7日枠」は金額ではないが、消費の大小関係はほぼ同じと見ている [推測]
