### 調査メモ（出典付き）
1. **Anthropic のマルチエージェント研究システム**（orchestrator-worker 型）
   - リード（Opus 4）＋サブエージェント（Sonnet 4）構成が単一 Opus 4 を社内評価で 90.2% 上回った。トークン消費はチャットの約15倍、エージェント単体で約4倍。ブラウジング評価の性能分散の 80% はトークン使用量だけで説明できた。
   - サブエージェントへの委任には「目的・出力形式・使うツール/情報源・タスク境界」が必要。曖昧だと重複作業や調査漏れが起きた。
   - 労力の目安: 単純な事実確認は1エージェント/3〜10ツール呼び出し、比較は2〜4サブエージェント、複雑な調査は10以上。
   - 成果はサブエージェントが外部ストレージ（ファイル）に保存し、リードには軽い参照だけ返す（「伝言ゲーム」とトークン浪費の回避）。
   - 評価は LLM-as-judge（事実の正確さ・引用の正確さ・網羅性・情報源の質）＋人間レビュー。引用は専用の citation エージェントで後付け。
   - 出典: https://www.anthropic.com/engineering/multi-agent-research-system
2. **長時間エージェントのハーネス**（Anthropic）
   - 失敗パターン: 一気にやろうとして半端に終わる、早すぎる「完了」宣言、検証不足、次のセッションに壊れた状態を残す。
   - 対策: 初回に initializer が環境を用意（要件リスト JSON の各項目に `passes:false`、進捗ファイル `claude-progress.txt`、git の初回コミット）。各セッションは「進捗ファイルと git log を読む→基本動作確認→1項目だけ進める→コミットと進捗更新」。テスト項目を消したり書き換えたりするのは禁止と明記。
   - 出典: https://anthropic.com/engineering/effective-harnesses-for-long-running-agents
3. **MAST: マルチエージェントの失敗分類**（Cemri et al., 2025）
   - 7つのフレームワークのトレースを分析し、14の失敗モードを3分類に整理: システム設計の問題 44.2%、エージェント間の不整合 32.3%、タスク検証の不備 23.5%（アノテータ一致度 κ=0.88）。
   - 出典: https://arxiv.org/abs/2503.13657 （arxiv はこの環境から取得できず、検索結果の要約と https://github.com/multi-agent-systems-failure-taxonomy/MAST で確認。14モードの内訳は未確認）
4. **マルチエージェント討論**（Du et al., ICML 2024）
   - 同じ LLM の複数インスタンスが回答を交換し、数ラウンド批判し合うことで推論と事実性が改善した。
   - 出典: https://proceedings.mlr.press/v235/du24e.html
   - 反論側の論文あり: "Stop Overvaluing Multi-Agent Debate"（https://arxiv.org/pdf/2502.08788）。タイトルから見る限り、討論の効果は評価方法次第でモデルの異質性が重要という主張（**推測**: 本文未読。agent4 に確認を依頼）。

### 本プロトコル自体の観察（問い5の材料）

- **O2 BOARD の表は衝突しやすい**（**推測**、次サイクルで実際の衝突ログを確認）: 5人の行が隣接しているので、同時に編集すると git の同じ hunk に入りやすく、rebase で衝突しやすい。→ `board/agentN.md` に分割するか、追記だけのログ形式に変える案。
